## 1. 獨立 GCP 專案

為什麼要獨立：LineSleuth 和 RepSafe 都用 Gemini 和 Cloud Run，帳混在一起就分不出誰燒了錢，停損⑤也沒辦法只看 RepSafe 的費用。

步驟（主控台名稱以實際畫面為準）：

1. Cloud 主控台 → 建立專案，名稱建議 `repsafe`（專案 ID 由 GCP 產生或自訂，**只填在本機 `.env` 和部署指令，不寫進公開文件**）。
2. 帳單 → 把這個專案連結到老闆的帳單帳戶。
3. 啟用 API：Vertex AI API（`aiplatform.googleapis.com`）、Web Risk API（`webrisk.googleapis.com`）、Cloud Run、Cloud Build、Artifact Registry（`gcloud run deploy --source` 會用到後兩個）。
4. 權限設定照 `docs/engineering/architecture.md` 第 8 節（Eddie 負責；Web Risk 需要的 IAM 角色待確認）。
5. 做完第 2、4 節的預算和配額設定**之後**，才第一次部署。

要先確認的兩件事：

- 老闆的帳單帳戶是否還在**免費試用期或有抵免額（credits）**：有的話，要注意預算的計算方式有沒有扣掉抵免額（見第 2 節第 5 步）。額度多少待老闆到帳單頁確認。
- 主辦或 Google Cloud 是否提供參賽者**抵免額**：待問主辦（可以併進 Quinn 的 `docs/qa/organizer-inquiry-draft.md`）。**預算以「沒有抵免額」來規劃**，拿到了是額外的。

## 2. 預算與 50／90／100% 警示設定步驟

官方說明：Cloud Billing「Create, edit, or delete budgets and budget alerts」（https://cloud.google.com/billing/docs/how-to/budgets）。

1. 主控台 → 帳單 → 預算與快訊（Budgets & alerts）→ 建立預算。
2. **範圍（Scope）**：專案只勾 RepSafe 那個專案；服務選「全部」。**不要**選整個帳單帳戶，不然 LineSleuth 的費用會混進來。
3. **預算類型**：選「指定金額」，不要選「上個月的支出」（新專案上個月是 0）。
4. **金額**：填第 3 節拍板的 100 SGD（帳單帳戶幣別是 SGD）。**2026-09-24 已設定完成。**幣別會跟著帳單帳戶走（官方價目表多半用 USD，換算匯率見第 5 節）。
5. **抵免額**：如果帳單帳戶有抵免額，建議把預算設成**用「扣抵免額之前」的費用計算**（選項名稱待老闆在畫面上確認）。否則抵免額吃掉費用，警示永遠不會響，等抵免額用完才發現燒得很快。
6. **門檻**：新增三條，全部選「實際支出（Actual）」：50%、90%、100%。另外可以加一條「預測支出（Forecasted）100%」當提早預警。

### 3.2 真 Gemini 接通後的複核

接上真 Gemini、跑完一輪評測（含截圖）後，我照下面的公式算一次：

```
估算總費用 = Σ（各期間的分析次數 × 單次分析成本）＋ 固定費用
複核值     = 估算總費用 × 緩衝倍數（2）
```

- **複核值 > 100：回報老闆**，由老闆決定調高上限、還是砍呼叫次數（少跑幾輪評測、公開展示期間調低速率上限）。我不自己改上限。
- 複核值遠小於 100：照樣維持 100，不用調（上限只是暫時防線，不是要花完）。但檢查一仍要做。

### 3.3 公式的說明與兩項檢查

- **緩衝倍數**：建議 **2 倍**。理由：呼叫次數和 token 數都是估算，評測可能要多跑好幾輪。不建議超過 3 倍：上限設太高，100% 警示就等於沒有用。
- **檢查一：最壞情況要夠早響**。用第 4.3 節的「程式上限打滿一天的費用」除以預算上限。如果被人灌爆 **1 天**就會超過 100%，這個上限就算合理；如果要被灌好幾天才會響，就要把上限調低，或把程式的每小時上限調低。帳單資料本身有延遲（官方說明有提到，實際延遲多久待查證），所以警示一定比實際扣款晚。

## 4. 警示不會停止扣款：四道真正的防線

**預算警示只會寄信，不會自動停止任何服務，也不會停止扣款。**真正能限制花費的是下面這幾道：

### 4.1 Cloud Run：最小實例 0、最大實例 1

- **實際部署設定是 `--min-instances 0 --max-instances 1`**（`docs/engineering/deploy.md`「目前設定」與重新部署指令；2026-09-25 從原本寫的 2 改成 1）。
- 最小實例 0：沒有人用的時候不收 CPU／記憶體費用（計費方式以 Cloud Run 價目表為準，待查證）。代價是冷啟動，錄影、評審前先打 `/health` 暖機。
- 最大實例 1：同時只有 1 個實例，記憶體內的速率計數器就是全服務的上限，灌爆時的最壞值比 2 台時少一半。
- 部署後到 Cloud Run 服務頁確認這兩個數字真的生效；之後任何人重新部署，都要照 `deploy.md` 的指令帶 `--max-instances=1`。

### 4.2 Gemini 與 Web Risk 的 API 配額

- 位置：主控台 → IAM 與管理 → 配額與系統限制（Quotas & System Limits），分別搜尋 Vertex AI API、Web Risk API。
- 目標：找有沒有「每天」的配額指標可以**往下調**；如果只有「每分鐘」的指標，就把每分鐘上限調到夠錄影和評測用就好。
- **Vertex AI 的 Gemini 能不能設每日上限，我沒辦法確認，待查證**（官方頁面：Vertex AI 生成式 AI 的配額說明 https://cloud.google.com/vertex-ai/generative-ai/docs/quotas ）。如果不能設，第 4.3 節的程式上限就是 Gemini 費用的主要防線。
- 配額超過時，Gemini 會回 429、Web Risk 會失敗，畫面顯示灰卡（Eddie 已經實作），不會變成琥珀卡。

### 4.3 程式的全服務速率限制

- 設定：`GLOBAL_RATE_LIMIT_PER_HOUR`，預設 120（`.env.example`）。`/api/analyze` 和截圖讀字 `/api/extract-text` 共用同一個計數器；超過上限就不呼叫 Gemini 和 Web Risk。
- 計數器存在記憶體、每個實例各算各的，所以**實際上限 = 設定值 × 最大實例數**；最大實例是 1，所以就等於設定值。
- 截圖開啟後（2026-09-24 拍板），灌爆時最貴的是一直上傳 10MB 大圖打 `/api/extract-text`：它和分析共用計數器，所以次數上限不變，但**單次成本比文字判斷高**。算下面的最壞費用時，Gemini 那一項用「截圖單次成本」和「判斷單次成本」中較高的那個（第 6 節）。
- **thinking tokens**：`gemini-3-flash-preview` 預設會思考（9/25 送 "ping" 就用了 13 個 thinking tokens，見 `deploy.md`），每次 Gemini 呼叫的成本都要含 thinking tokens（第 6 節）。
- 最壞情況（有人一直灌，程式上限全打滿；2026-09-25 依最大實例 1 重算）：

```
每天最多分析次數   = GLOBAL_RATE_LIMIT_PER_HOUR × 最大實例數 × 24
                  = 120 × 1 × 24 = 2,880 次（照目前設定值 120）
每天最多 Gemini 呼叫 = 每天最多分析次數 × (1 + GEMINI_MAX_RETRIES)      ← 預設重試 1 次，最壞 5,760 次
每天最多 Web Risk 查詢 = 每天最多分析次數 × MAX_URLS_CHECKED           ← 預設 5，最壞 14,400 次
程式上限打滿一天的費用 = Gemini 呼叫 × 單次 Gemini 成本（含 thinking，第 6 節）
                      ＋ Web Risk 查詢 × 單價 ＋ Cloud Run 費用          ← 單價全部待查證
```

| 設定值 | 每天最多分析 | 每天最多 Gemini 呼叫 | 每天最多 Web Risk 查詢 | 一天最壞費用 |
|---|---|---|---|---|
| 120（開發、評測、錄影） | 2,880 | 5,760 | 14,400 | `[ ]`（單價待查證） |
| 30（公開展示，建議） | 720 | 1,440 | 3,600 | `[ ]`（單價待查證） |

- 第 3.3 節檢查一要用上表的「一天最壞費用」除以 100 SGD 重做一次；9/28 拿到 token 數後我來算。
- 已知小漏洞：實例重啟或重新部署時計數器歸零（`deploy.md`「已知限制」），一小時內重啟多次，實際次數會比上表多。以預算警示和 Vertex AI 每日配額（`deploy.md` 第 5 步）補位。
- 財務建議（**待老闆拍板**，只改環境變數、不改程式）：
  - 開發、評測、錄影期間：維持 120（評測一輪 33 則 × 2 次＋5 則，約 71 次，夠用）。
  - **10/12 之後的公開展示期間：調低到 30**（估算：評審一小時內按超過 30 次的機會很低）。這樣最壞情況直接變成四分之一。

### 4.4 100% 警示時：停止所有雲端呼叫

以下由輕到重，選一個做（實際指令請 Eddie 確認）：

1. **把 Cloud Run 服務刪掉或改成不公開**：最快，Gemini、Web Risk 就不會再被呼叫。程式和映像檔都還在，之後可以重新部署。
2. **停用 Vertex AI API 和 Web Risk API**：服務還開著，但每次都會顯示灰卡。

## 6. 單次分析成本公式

```
單次分析成本 =
    Gemini 判斷：  (輸入 tokens × 輸入單價 ＋ (輸出 tokens ＋ thinking tokens) × 輸出單價) ÷ 1,000,000 × (1 + 重試率)
  ＋ 截圖讀字：    截圖占比 × 每則平均截圖張數 × 截圖單次成本 × (1 + 截圖重試率)                    ← 2026-09-24 拍板做截圖，此項不再是 0
                  截圖單次成本 = 圖片輸入成本（每張圖折算 tokens × 輸入單價 ÷ 1,000,000，或按張單價，待查證）
                               ＋ 文字提示 tokens × 輸入單價 ÷ 1,000,000
                               ＋ (輸出 tokens ＋ thinking tokens) × 輸出單價 ÷ 1,000,000
  ＋ Web Risk：    平均每則連結數 × Web Risk 每次單價                                                ← 在免費額度內為 0
  ＋ Cloud Run：   平均處理秒數 × (vCPU 數 × vCPU 秒單價 ＋ 記憶體 GiB × GiB 秒單價) ＋ 每次請求單價
```

- 單價的單位要對齊：價目表如果是「每 1M tokens」，就照上式除以 1,000,000；如果是別的單位，照價目表換算。
- **thinking tokens（2026-09-25 新增）**：`gemini-3-flash-preview` 預設會思考，連送 "ping"（輸入 1 token）都用了 13 個 thinking tokens（`deploy.md` 第 3 步）。真正的詐騙判斷要讀整段對話，thinking tokens 估計會多很多（估算，**待 9/28 看 log 的 `thinking_tokens`**）。我先**按輸出單價計**，比較保守；價目表如果另列 thinking 單價，查證後改用那個。thinking 可能是 Gemini 費用最大的一塊，要不要限制思考量是 Eddie 的技術判斷（會影響準確率和延遲），我只提供成本數字。
- **tokens 從哪來**：Eddie 的 log 每次都會記 token 數（`docs/engineering/architecture.md` 第 5、8 節）。接上真 Gemini 後，用評測集跑一輪，取**平均值和最大值**各算一次；預算用最大值算，比較保守。
- **重試率**：log 裡有問題代碼，算「有重試的次數 ÷ 總次數」；還沒有資料前先用最壞值 1（每次都重試）。
- **平均每則連結數**：評測集 33 則裡的連結總數 ÷ 33。
- **截圖占比、張數**：截圖占比 = 用截圖送出的分析次數 ÷ 總分析次數；還沒有資料前，預算用最壞值（占比 1、每則 1 張）算。截圖讀字失敗時會不會重試、重試幾次，請 Eddie 確認；確認前先用最壞值 1。
- **截圖的 token 數**：接上真 Gemini 後，用盲測截圖和錄影用截圖各跑幾張，從 log 讀圖片呼叫的輸入 tokens，大圖、小圖分開記（估算：手機截圖尺寸差不多，但 10MB 上限的大圖可能明顯較貴，待實測）。
- 固定費用（不隨次數變動）：Artifact Registry、Cloud Build、Cloud Storage，每月估一次，另外加在總費用裡。
